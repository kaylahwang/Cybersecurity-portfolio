# RFC 3227 – Guidelines for Evidence Collection and Archiving

## Overview

RFC 3227 provides best-practice guidance for collecting and preserving evidence following a security incident.

Its objective is to maximise the evidential value of collected data while minimising the risk of alteration or contamination.

RFC 3227 remains one of the foundational references in digital forensics and incident response.

---

## Purpose

The document provides guidance for handling evidence related to:

- Security incidents
- Malware infections
- Data breaches
- Unauthorised access
- System compromises
- Insider threats

The focus is evidence collection and preservation rather than evidence analysis.

---

## Guiding Principles

### Follow Organisational Procedures

Evidence collection should align with organisational security policies and incident response procedures.

---

### Keep Detailed Notes

Investigators should document:

- Dates and times
- Actions performed
- Commands executed
- Observations made

Documentation may become critical during legal proceedings.

---

### Collect Before Analysis

Evidence should be collected before any detailed analysis is performed.

Analysing a live system can alter evidence and reduce its evidential value.

---

### Minimise Changes

Investigators should minimise changes to:

- File contents
- Metadata
- Access timestamps
- System state

---

### Be Methodical

Evidence collection should be:

- Repeatable
- Transparent
- Documented
- Defensible

---

## Order of Volatility

Evidence should be collected from most volatile to least volatile.

### Highest Volatility

1. CPU Registers
2. CPU Cache

### High Volatility

3. Routing Tables
4. ARP Cache
5. Process Tables
6. Kernel Statistics
7. RAM

### Medium Volatility

8. Temporary File Systems

### Lower Volatility

9. Hard Drives
10. Remote Logs
11. Physical Configuration
12. Network Topology
13. Archive Media

Collecting volatile evidence first reduces the risk of losing critical information.

---

## Things to Avoid

### Do Not Shut Down the System Immediately

Shutdown may destroy valuable evidence such as:

- RAM contents
- Running processes
- Active network connections

---

### Do Not Trust Local Utilities

A compromised system may contain modified or malicious tools.

Whenever possible, investigators should use trusted external forensic tools.

---

### Avoid Altering Evidence

Activities that modify evidence should be avoided whenever possible.

This includes changes to:

- File access timestamps
- Metadata
- System configuration

---

## Evidence Collection Procedure

1. Identify affected systems
2. Determine relevant evidence sources
3. Assess evidence importance
4. Follow the order of volatility
5. Remove opportunities for external change
6. Collect evidence
7. Record clock drift and timestamps
8. Document all actions

---

## Chain of Custody

Chain of custody records:

### Discovery

- Where evidence was found
- When evidence was found
- Who discovered it

### Handling

- Who accessed the evidence
- When access occurred

### Storage

- Storage location
- Storage conditions
- Security controls

### Transfer

- Evidence transfers
- Changes in custody
- Transportation records

Maintaining chain of custody helps demonstrate authenticity and integrity.

---

## Evidence Archiving

Evidence should:

- Be securely stored
- Have restricted access
- Be protected from alteration
- Be clearly documented

Any access to archived evidence should be recorded.

---

## Tools Mentioned in RFC 3227

Examples include:

### System Information

- ps
- ifconfig
- netstat
- arp

### Acquisition

- dd
- SafeBack

### Integrity Verification

- sha1sum
- PGP

### Memory Analysis

- gcore
- gdb

---

## Key Takeaway

The most important forensic principle introduced by RFC 3227 is:

> Collect evidence first. Analyse evidence later.

Protecting evidence integrity is more important than immediate investigation.
